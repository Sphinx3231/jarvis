# Jarvis Mobile

A native Android companion (Kotlin, Jetpack Compose) with two modes:

- **Remote PC** — the phone controls your PC's Jarvis from anywhere. The PC does the work, with its
  own approvals and safety controls. The phone shows the connection, agents, tasks, approvals,
  results, and whether each command was *accepted* by the PC or *completed*.
- **Mobile** — Jarvis runs on the phone itself: its own conversations, memory, reminders, native
  capabilities, permission policy and voice. It is not a front end for the PC.

```
 Android phone                      Relay (you host)                    PC
┌──────────────────────┐          ┌──────────────────┐          ┌──────────────────────────┐
│ RemoteSession        │──wss────▶│ authenticates     │◀──wss────│ MobileGateway            │
│  E2E (AES-256-GCM)   │  outbound│ routes sealed     │ outbound │  scopes, idempotency,    │
│  outbox + idempotency│          │ frames, allow-list│          │  replay window, rate     │
│ Keystore identity    │          │ no plaintext,     │          │  limit, audit            │
│                      │          │ no history        │          │  → app.jarvis / engine / │
│ Mobile runtime       │          └──────────────────┘          │    permissions (as-is)    │
│  router · tools ·    │                                        └──────────────────────────┘
│  permissions · Room  │──https──▶ your model provider (Mobile mode only, if configured)
└──────────────────────┘
```

Nothing on the PC listens on the network: the PC and phone both connect *out* to the relay.

## Protocol

Every message between phone and PC is an envelope
`{v, id, sessionId, from, to, ts, type, payload, correlationId?, idempotencyKey?}`, sealed with
AES-256-GCM and carried in a relay `msg` frame. Types: `device.pair.request/confirm/reject`,
`device.status`, `device.revoke`, `jarvis.command.submit/accepted/rejected`,
`jarvis.response.delta/complete`, `agent.status.changed`, `agent.run`,
`task.created/progress/completed/failed/cancel`, `approval.requested/resolve/resolved`,
`voice.session.started`, `voice.transcript`, `pc.snapshot.request`/`pc.snapshot`,
`system.emergency_stop`/`system.stopped`, `connection.heartbeat`, `error`.

Consequential messages carry an idempotency key; the PC answers retries from its ledger
(`mobile_commands`) and never executes twice. Envelopes older/newer than ±5 minutes or with a
seen id are dropped.

## Security model

- **Relay possession ≠ permission.** The relay only routes. The PC authorizes every message
  itself: known, un-revoked device → scope check (`observe`, `command`, `approve`, `stop`) →
  idempotency → rate limit (30 commands/min) → the *existing* Jarvis path (`app.jarvis`,
  `app.engine`, `app.permissions`). Phone commands get the same approvals and checks as typed ones;
  the phone can answer an approval only with the `approve` scope.
- **Pairing**: the PC shows a QR with a one-time room, a 256-bit secret and its own device id. The
  pairing exchange is encrypted with a key derived from the secret, the PC's identity is pinned
  from the QR, at most 5 bad attempts, expires in 5 minutes, one phone per code. The phone always
  asks for confirmation before pairing, including from a `jarvis://pair` link.
- **Keys**: phone keys are in the Android Keystore (non-exportable); PC keys are in Jarvis's
  encrypted secret store. Standard algorithms only (P-256, HKDF-SHA256, AES-256-GCM, ECDSA).
- **Permanent pairing**: a pairing lasts until the user presses Unpair (phone) or Unpair (PC).
  Restarts of Jarvis, the PC, the relay or the phone don't affect it; both ends reconnect on their
  own and queued commands are re-sent (and de-duplicated).
- **Mobile mode** never runs an action just because the model asked: every tool call is validated
  against its schema, checked for availability, and authorized by policy (read-only → allow,
  acting → ask, user can set allow/ask/block per capability). Approvals only come from the user's
  tap. Android permissions are requested only when a feature needs them. No AccessibilityService,
  no always-on wake word (push-to-talk only), no silent uploads: nothing leaves the phone except
  requests to the model provider the user configured.

## On-device model (Mobile mode default)

The APK can ship its own model, so Mobile mode works offline with no account: **Qwen2.5-1.5B-Instruct**
(Apache-2.0, int8, 1.6 GB, packaged for on-device inference by Google's litert-community), run with
MediaPipe LLM Inference (GPU when available, otherwise CPU). On first launch it's copied out of the
APK into app storage once (needs ~1.7 GB free on top of the app); it is released when Android asks
for memory.

- **Direct commands first.** A 1.5B model is unreliable at choosing tools, so clear commands
  (alarms, timers, reminders, search, open app/site, call, copy, battery, network, remember/recall,
  time, date) are understood by `LocalIntents` and never reach the model. They still go through
  validation and approvals.
- **The model handles the rest**: conversation, questions, and paraphrased actions via a
  `CALL tool {json}` line that the router validates and authorizes like any other call. A reply that
  claims an action or reading without a tool gets a visible note that nothing was done.
- **Why not DeepSeek-R1-Distill-1.5B?** It was tested first, on the same file format and prompts. It
  ignored instructions, gave canned "I'm DeepSeek-R1" replies, produced malformed or dangerous tool
  calls (it tried to dial a made-up number) and in reasoning mode looped for thousands of tokens.
  Qwen2.5-1.5B-Instruct was clearly better on every case.
- **Measured.** `mobile/scripts/local-model-check.sh` sends the app's exact prompts through the real
  model (LiteRT-LM on a computer) and parses the replies with the app's parser: 9 of 10 scenarios
  behave as expected and the tenth bad call is refused by validation. The one miss ("how charged is my phone" → an
  invented percentage) is a direct command in the app, and is flagged by the honesty note otherwise.

Build with the model: `mobile/scripts/fetch-model.sh`, then
`./gradlew assembleDebug -Pjarvis.bundleModel=true` (APK ≈ 1.7 GB). Without the flag the APK has
no model and Mobile mode offers cloud models or direct commands.

## Build and install the app

Needs JDK 17+ and the Android SDK (platform 35). From `mobile/android/`:

```sh
echo "sdk.dir=$ANDROID_HOME" > local.properties     # once
./gradlew assembleDebug                              # → app/build/outputs/apk/debug/app-debug.apk
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

`./gradlew assembleRelease` builds a minified APK (`app/build/outputs/apk/release/app-release.apk`),
signed with the debug key so it installs directly; replace the signing config before publishing.
Without adb: copy the APK to the phone and open it (allow "install unknown apps" for your file
manager).

## Limits (honest)

- No emulator/device was available while building this, so the app has been verified by JVM and
  Robolectric tests, rendered screenshots and the cross-language end-to-end test — not yet on a
  physical phone. Camera QR scanning, SpeechRecognizer, TTS and the Android intents behind the
  tools need an on-device check.
- Android may suspend the relay connection when the app is in the background; it reconnects as
  soon as the app is opened or the network returns. There is no background service, so PC
  approvals don't push to the phone while the app is closed.
- Cross-network use needs a relay you deploy with TLS (see `relay/README.md`).
- Streaming replies (`jarvis.response.delta`) are defined in the protocol but the PC currently
  sends the complete reply.
- The on-device model is small: good for chat and simple requests, not for complex multi-step work. It has been validated on a computer with the same model file, not yet on a phone (speed and GPU support vary by device).
